Chapter 3: CPU 虚拟化

之前我们已经知道，一个 Process 本质上就是正在执行中的 Program。但一台单核 CPU 在某一瞬间实际上只能执行一个 Process，于是马上会出现一个问题：如果系统里同时有几十个 Process，为什么我们平时完全感觉不到“只有一个人在跑”？

答案就是 CPU Virtualization。

所谓 Virtualizing CPU，并不是真的给每一个 Process 创建一颗假的 CPU。Process 仍然是直接跑在真实 CPU 上的，只不过 OS 不断让 Process A 跑一会、停下来，再让 B 跑、再停下来，再让 C 跑。只要这种切换足够透明，每个 Process 就会感觉自己好像一直拥有一颗 CPU。

所以 CPU Virtualization 的核心并不是制造虚拟硬件，而是 Context Switching：让不同 Process 轮流直接使用真实 CPU，同时保证被暂停的 Process 以后还能从原来的地方继续执行。

从 User Mode 进入 Kernel

Process 平时在 User Mode 下直接使用 CPU 运行自己的代码，但有些事情 User Program 没有权限自己做，例如访问文件、申请某些受保护资源等等。这时候 Application 必须请求 OS 服务，也就是进行 System Call。

课件把这件事情放在 CPU Virtualization 前面，是因为 Context Switch 本身最终也一定要由 Kernel 完成，所以首先要搞清楚：CPU 到底是如何从 User Program 进入 Kernel 的。

不过 Application 一般不会自己手搓底层 System Call，而是调用更高层的 API，例如 Unix/Linux 程序通常通过 POSIX API 以及 C Library 来访问 OS 服务。API 的意义很直接：Programmer 只需要知道这个函数怎么调用、参数是什么、返回什么，而不用知道当前 OS 和 CPU 究竟使用哪条 Assembly Instruction、参数应该塞进哪个 Register。

User Stack、Kernel Stack 和 PCB

这里非常容易把几个名词混成一坨。首先，Stack 不是 Running Log。Stack 不是“从程序启动到现在发生过什么”的完整历史记录，而是一块按照 Stack 方式使用的 Memory，用来保存当前 Execution Chain 还需要的数据，例如 Function Call Frame、Local Variables、Return Address、暂存下来的 Register Values 等等。

Fault

Fault 表示 CPU 在 Instruction 完成之前检测到了问题，例如 Lecture 给的 Page Fault、Segmentation Fault。其中有些 Fault 是可以被修复的，处理完以后原 Program 还能继续运行。所以不要直接理解成 Fault = Program 必死，并不是。

Trap

这页把 Trap 定义为 CPU 在 Instruction 执行之后检测到 Exception，并且处理后 Program 可以继续，Lecture 举的例子是 INT Instruction。需要注意，这门课前面还会用 trap into kernel 来泛指“受控进入 Kernel”的动作，所以这里有两个不同语境：trap into kernel 强调的是进入 Kernel 这个动作，而 Fault / Trap / Abort 里面的 Trap 是 Exception Classification。不要把两层含义强行混成一个。

Abort

Abort 表示 CPU 遇到了不可恢复的严重错误，Lecture 例子是 Double Fault，也就是处理一个 Fault 的过程中又发生另一个 Fault。这种情况通常已经不能正常回到 Current Program 继续执行。

总结

这一章实际上一直在回答三个问题。第一，Application 需要做 Privileged Operation 怎么办？答案是 System Call。第二，一颗 CPU 怎么让多个 Process 感觉自己都有 CPU？答案是 Context Switch。第三，如果 Process 根本不合作，OS 怎么保证还能拿回 CPU？答案是 Interrupt。

整条故事连起来就是：

所以所谓 Virtualizing the CPU，本质并不玄学：Process 真的直接运行在真实 CPU 上；OS 通过 System Call 和 Interrupt 重新获得控制权，再通过 Context Switch 在不同 Process 之间切换真实 CPU 的执行现场，于是每个 Process 都获得了“我好像一直有一颗 CPU”的假象。

一句话 Takeaway：System Call 解决“User Program 怎么安全进入 Kernel”，Interrupt 解决“Kernel 怎么保证一定能重新拿回 CPU”，Context Switch 解决“Kernel 拿回 CPU 以后怎么从 A 无缝换到 B”；这三件事情一起构成了 CPU Virtualization 最核心的 Mechanism。
